Verifikationsstand dieser Ausgabe
Das erste reale Board (Waveshare ESP32-S3-ETH+PoE, nur interner Sensor bestückt, kein OLED gesteckt) wurde am 18.07.2026 erstmals in Betrieb genommen. Auf echter Hardware bestätigt: PoE-Stromversorgung, LAN-Verbindung, Weboberfläche/REST-API, interner Sensor, NTP-Zeitsynchronisierung (inkl. Zeitzonen-Fix), SNMP-Grundfunktion sowie ein OTA-Update per USB-Neuflash. Noch nicht auf echter Hardware verifiziert: OLED-Anzeige (kein Display gesteckt), externes SH1107-Modul, Relais/Aktor, Kontaktmodul, Sensor 2 (RJ45), MQTT gegen einen echten Broker, Branding-Logo-Upload sowie ein Werksreset über Taster/Weboberfläche. Entsprechende Abschnitte sind unten einzeln gekennzeichnet.

1Erste Inbetriebnahme

1.1 Auspacken & Hardware-Übersicht

Das Gerät basiert auf dem Waveshare ESP32-S3-ETH-Modul (ESP32-S3R8, Dual-Core, 8 MB Octal-PSRAM im Chip-Package/16 MB Flash — PSRAM wird von der Anwendung aktuell nicht genutzt) mit W5500-Ethernet-PHY über SPI statt eines nativen RMII-PHY, ergänzt um einen internen DHT22-Sensor, ein OLED-Display SSD1306 (0,96", 128×64, I2C) und einen RJ45-Modularanschluss für Sensor 2, Relais oder Kontaktmodul. Anders als die Geschwisterprojekte Sensormeter (WT32-ETH01) besitzt dieses Board natives USB für Programmierung und serielle Kommunikation — keine externe Debug-Burning-Schnittstelle nötig. Genaues Pin-/Verkabelungsschema: docs/verdrahtungsplan.html, Hersteller-Pinout: docs/ESP32-S3-ETH-Datenblatt.pdf / docs/ESP32-S3-ETH-Schematic.pdf.

Anders als Sensormeter (WT32-ETH01, ohne Onboard-USB, muss über eine externe Debug-Burning-Schnittstelle mit manuellem Boot-Modus-Wechsel geflasht werden) hat dieses Board ein natives USB-C über das sowohl geflasht als auch die Serial-Kommandozeile (Abschnitt 8) bedient wird — kein zusätzlicher USB-Seriell-Adapter, kein manuelles Halten von EN/IO0 nötig. Am ersten realen Testboard funktionierte der automatische Upload über pio run --target upload ohne jeden manuellen Handgriff. Der abgebildete RJ45-Modularanschluss ist ein separater Stecker für Sensor 2/Relais/Kontakt — nicht zu verwechseln mit der Ethernet-RJ45-Buchse für das Netzwerkkabel (Abschnitt 4.2 „Externe Schnittstelle" bzw. Abschnitt 6 für die PoE-Stromversorgung).

PoE optional, kein Zwang
Je nach bestücktem Board/Zubehör kann die Stromversorgung über ein PoE-Modul am Ethernet-Port erfolgen (am ersten Testgerät so verifiziert) — alternativ funktioniert auch eine normale USB-C-Versorgung. Für Details zum Strombudget der 5V-Schiene, die zusätzlich am RJ45-Modularanschluss (Pin 8) zur Verfügung steht, siehe docs/verdrahtungsplan.html.

1.2 Flash-Bereitschaft herstellen

Da natives USB vorhanden ist, entfällt der bei Sensormeter (WT32-ETH01) nötige externe USB-Seriell-Adapter samt manuellem EN/IO0-Handling vollständig:

  1. Board per USB-C-Kabel an den PC anschließen (liefert bereits genug Strom zum Flashen, kein separates Netzteil nötig)
  2. Treiber: Windows erkennt das native USB-CDC-Gerät in der Regel ohne zusätzlichen Treiber; erscheint kein COM-Port, siehe Anhang
  3. Kein manueller Boot-Modus-Wechsel nötig — der Onboard-BOOT-Taster (GPIO0, Abschnitt 3) ist im Normalbetrieb frei für Seitenwechsel/Werksreset nutzbar und muss beim Flashen nicht gehalten werden

1.3 PowerShell-Skript ausführen

Das Skript scripts/flash.ps1 übernimmt die komplette Einrichtung: es fragt zuerst, welches der vier Sensormeter-Projekte geflasht werden soll (dasselbe Skript liegt identisch in allen vier Repos), installiert dann fehlende Werkzeuge (Python, Git, PlatformIO), holt den Quellcode, legt bei Bedarf firmware/include/config.h an und baut/flasht die Firmware.

.\flash.ps1 -Project poe

Der Toolchain-Installer (idf_tools.py) bricht unter Git-Bash/MSYS mit „MSys/Mingw is not supported" ab — Skript und alle pio-Aufrufe für dieses Projekt müssen unter echtem PowerShell laufen (docs/entscheidungen.md).

1.4 Flashen

Ohne -SkipUpload schließt das Skript direkt mit dem eigentlichen Flash-Vorgang ab (pio run --target upload). Das Board bootet danach automatisch neu.

Bei Fehlschlag
Häufigste Ursachen: falscher COM-Port, USB-Kabel ohne Datenleitungen (reines Ladekabel), oder ein anderes Programm blockiert den seriellen Port (z. B. ein offenes Terminalfenster). Ein inkrementeller Build nach einem zuvor abgebrochenen Flash-Vorgang kann vereinzelt fehlschlagen — in dem Fall hilft ein kompletter Neubau (.pio\build\esp32-s3-eth löschen, dann erneut pio run --target upload).
Einstellungen bleiben beim Flashen erhalten
Ein normaler Flash-Vorgang schreibt ausschließlich den App-Bereich (Bootloader, Partitionstabelle, Firmware-Image). Die separate LittleFS-Datenpartition, auf der config.xml, history.csv und log.txt liegen (siehe Abschnitt 7), bleibt dabei unangetastet — LAN/WLAN-Zugangsdaten, statische IP, Web-Passwort etc. gehen beim Neuflashen also nicht verloren. Nur ein expliziter kompletter Flash-Löschvorgang oder ein Werksreset über die Weboberfläche (Abschnitt 4.2) setzt sie zurück.

2Erststart am Gerät

Die Netzwerk-Ersteinrichtung läuft über die Weboberfläche (Abschnitt 4), erreichbar sobald das Gerät im Netzwerk ist. Wie bei Sensormeter gibt es zwei Netzwerk-Interfaces: LAN (Ethernet über den W5500, primär) und optional WLAN parallel dazu.

2.1 Boot-Ablauf

  1. BOOT / INIT — kurze Initialisierung, das OLED zeigt Systemname + Systemtyp und einen Countdown (sofern ein OLED gesteckt ist)
  2. NETWORK_CHECK — Ethernet startet automatisch (DHCP oder statisch), WLAN parallel dazu falls Zugangsdaten hinterlegt sind; bis zu 5 Minuten lang
  3. Bei Erfolg (LAN oder WLAN hat eine IP): Normalbetrieb, das OLED wechselt zu den rotierenden Infoseiten (Abschnitt 3)
  4. Haben nach 5 Minuten weder LAN noch WLAN eine IP: Fallback-Modus — das Gerät spannt einen eigenen Access Point auf (siehe Abschnitt 2.2)

Ist ein LAN-Kabel angeschlossen, ist der Fallback-Fall in der Praxis selten — er greift vor allem, wenn weder Kabel gesteckt noch ein WLAN konfiguriert ist.

2.2 Ersteinrichtung über den eigenen Access Point

Eigener Access Point „installer"

Findet das Gerät nach 5 Minuten weder über LAN noch über WLAN eine Verbindung, spannt es selbst ein Netzwerk auf: SSID installer, Passwort installer, feste IP 192.168.4.1, DHCP-Server aktiv. Kein Internetzugang über diesen Access Point. Das OLED zeigt währenddessen nur „Fallback aktiv" + die eigene IP (Abschnitt 3).

  1. Mit einem Smartphone, Tablet oder Laptop im WLAN nach installer suchen und mit Passwort installer verbinden
  2. Im Browser http://192.168.4.1/ aufrufen
  3. Auf der Einstellungsseite (Abschnitt 4, Login erforderlich) im Bereich „WLAN" SSID/Passwort eintragen und „Verbinden & testen (Neustart)" klicken
  4. Klappt die Verbindung, verlässt das Gerät den Fallback-Modus. Klappt sie nicht (und ist auch kein LAN-Kabel gesteckt), spannt es automatisch wieder den Access Point auf

Steckt stattdessen einfach ein LAN-Kabel — das genügt in den meisten Fällen, ganz ohne den Umweg über den Access Point.

3OLED-Anzeige

Das interne 128×64-SSD1306-Display (I2C-Adresse 0x3C) zeigt im Normalbetrieb sieben Infoseiten im 10-Sekunden-Takt (sechs Standardseiten + eine optionale Branding-Seite, siehe unten). Alle Seiten sind horizontal und vertikal zentriert und nutzen eine feste, bewusst große Schrift; passt eine Zeile nicht auf einmal (z. B. eine lange WLAN-SSID), läuft sie waagerecht durch, bis sie komplett zu lesen war, statt die Schrift zu verkleinern.

Fehlt das Display, bleibt es einfach dunkel
Vor jedem display.begin() prüft die Firmware per I2C-ACK-Probe, ob unter 0x3C überhaupt ein Gerät antwortet — erst bei echtem ACK wird das Display initialisiert. Ohne gestecktes OLED (wie beim ersten Testboard) meldet die Firmware das im Boot-Log einmalig und läuft ansonsten normal weiter, ohne endlose I2C-Fehlermeldungen zu erzeugen (früherer Bug, siehe docs/entscheidungen.md).

BOOT-Taster gehalten (Reset-Bestätigung)
Anders als Sensormeter (WT32-ETH01, GPIO0 fest als Ethernet-Takteingang belegt, kein freier Taster) ist der Onboard-BOOT-Taster (GPIO0) hier frei nutzbar, da der W5500 komplett über SPI angebunden ist. Kurzer Tipp (unter 3s gehalten): sofortiger Seitenwechsel, wie ein manueller „nächste Seite"-Klick. 3s halten: Overlay „Werksreset? <n>s halten" mit 20s-Countdown. Wird der Taster jetzt losgelassen, passiert nichts — nur ein Loslassen nach Ablauf der vollen 23s (3s + 20s) löst den Reset tatsächlich aus (Fail-Safe: ein defekter, dauerhaft gedrückter Taster kann so nie von selbst einen Reset auslösen, da ein echtes Loslassen-Ereignis nötig ist). Nach Ablauf der 20s zeigt das Display „Loslassen zum Bestätigen". Der Reset setzt nur die Konfiguration zurück (wie Werksreset-Umfang „Nur Konfiguration", Abschnitt 4.2) — der 7-Tage-Verlauf bleibt erhalten. Noch nicht auf echter Hardware verifiziert (kein OLED am ersten Testboard gesteckt).

Kollisions-Check vor dem Setzen einer statischen IP
Wird bei LAN und/oder WLAN eine statische Adresse eingetragen und gespeichert, prüft das Gerät vor dem Übernehmen per Ping, ob im jeweiligen Netz bereits ein anderes Gerät unter dieser Adresse antwortet. Ist das bei mindestens einer der beiden Adressen der Fall, wird die Einstellung nicht übernommen und die Fehlermeldung „IP-Adresse belegt" angezeigt — einfach eine andere, freie Adresse wählen und erneut speichern. Der Check läuft pro Interface nur, wenn sich die eingetragene Adresse tatsächlich von der aktuell aktiven LAN- bzw. WLAN-IP unterscheidet.

Der Button „IP-Einstellungen übernehmen & neu starten" ist der sicherste Weg, gezielt nur die Netzwerkadresse eines Interfaces zu ändern: bei statischer IP wird sie vorab per Ping auf Kollision geprüft; bei DHCP schaltet das Gerät die laufende Verbindung testweise auf DHCP um und wartet auf eine tatsächlich erhaltene Lease, bevor etwas gespeichert wird. Schlägt der Test fehl, bleibt die bisherige Konfiguration unverändert aktiv, nichts wird gespeichert und kein Neustart ausgelöst.

Externe Schnittstelle

Gegliedert nach den zwei RJ45-Modulkategorien (siehe sensormeter-family/repo/module-design/README.md): Kategorie 1 (I2C-Bus, mehrere Module gleichzeitig möglich, rein automatisch erkannt) und Kategorie 2 (Direkt-Module auf dediziertem Einzelpin, jeweils genau eines gleichzeitig, manuell gewählt).

Kategorie 1 — Bus-Modul (I2C)

FeldBedeutung
Erkannter Modultyp/ChipNur-Anzeige — Ergebnis der automatischen RJ45-Modul-Erkennung. Bekannte Chips: BH1750 (Helligkeit), SHT30/31/35, AHT20/AHT21, BME280 (per Chip-ID-Register vom baugleichen BMP280 unterschieden), BMP280 (Luftdruck), ENS160 (Luftgüte/eCO2) — unbekannte I2C-Adressen werden als „unbekannt" gemeldet, statt ignoriert zu werden.
Automatische Modul-Erkennung
Läuft einmal beim Boot (parallel zur Netzwerk-Wartezeit) sowie erneut alle 60 Sekunden im laufenden Betrieb: scannt den kompletten I2C-Adressraum am RJ45-Bus (Pin 3/4, geteilt mit dem OLED — Display-Adressen 0x3C/0x3D werden übersprungen) und wertet dabei alle gefundenen Geräte aus (nicht nur das erste), damit auch Kombimodule (z. B. AHT20+BMP280) korrekt erkannt werden — genutzt wird weiterhin nur das primäre (niedrigste Adresse). Findet der I2C-Scan nichts und ist Pin 5 als „Sensor" konfiguriert, probiert die Erkennung zusätzlich einen DHT-Leseversuch auf Pin 5. Findet die Erkennung ein Modul, wird „Sensor 2 aktiv" automatisch gesetzt — ein bereits manuell deaktivierter Schalter wird dabei NIE stillschweigend wieder aktiviert. Ein ergebnisloser erneuter Scan (Modul entfernt) setzt „Sensor 2 aktiv" umgekehrt NICHT automatisch zurück. Nicht erkannt werden kann die Anwesenheit eines Relais- oder Kontaktmoduls (kein auswertbares Rück-Signal) sowie DHT11 vs. DHT21 (siehe „DHT-Typ" unten) — beides bleibt rein manuelle Auswahl.

Kategorie 2 — Direkt-Module

FeldBedeutung
Relais aktiv (Pin 6/7)Manuelles Schalten — ein Relais-Modul kann nicht automatisch erkannt werden. Unabhängig vom Pin-5-Modultyp, da sich die RJ45-Pins nicht überschneiden — ein Kombi-Modul mit Sensor/Kontakt UND Relais ist möglich.
Aktueller Zustand + „Relais schalten"Zeigt den zuletzt kommandierten Schaltzustand und schaltet ihn um. Startet nach jedem Neustart sicherheitshalber immer mit AUS (kein persistierter Zustand) — ein wieder angelaufenes Gerät reaktiviert einen zuvor eingeschalteten Verbraucher nicht stumm.
Automatisch schaltenAuswahl „Nein" (Default, rein manuell) oder „Sensor" — blendet bei „Sensor" die Felder Quelle/Wert/Bedingung/Schwellenwert bzw. Zustand ein. Wird bei jedem Durchlauf neu ausgewertet und überschreibt dabei ein manuelles Schalten.
Quelle (Automatik)Nur bei „Automatisch schalten" = „Sensor" sichtbar. Auswahl „Sensor 1 (intern)" / „Sensor 2 (extern)" / „Kontakt" als Datenquelle für die Schaltbedingung.
Wert / Bedingung / SchwellenwertNur bei Quelle „Sensor 1"/„Sensor 2" sichtbar. „Wert" wählt Temperatur oder Luftfeuchte, „Bedingung" größer/kleiner als, „Schwellenwert" den Vergleichswert.
Zustand (Automatik)Nur bei Quelle „Kontakt" sichtbar. Relais schaltet EIN, sobald der Kontakt den gewählten Zustand (Offen/Geschlossen) erreicht.
Modultyp Pin 5Auswahl „Sensor" oder „Kontakt" — beide Belegungen liegen auf demselben Pin und schließen sich gegenseitig aus.
Sensor 2 (extern) aktivNur bei Modultyp „Sensor" sichtbar. Aktiviert Sensor 2.
Sensor-2-NameFreier Anzeigename für Sensor 2 (Default „Extern").
DHT-TypNur relevant, falls tatsächlich ein DHT-Modul auf Pin 5 gesteckt ist (I2C-Module ignorieren dieses Feld). Auswahl „DHT11" oder „DHT21" (Default) — automatische Unterscheidung ist unzuverlässig, daher rein manuelle Wahl.
Sensor 2 Korrektur Temperatur/FeuchteWie Sensor 1, für den externen Sensor (nur bei Temperatur/Feuchte-liefernden Modulen wirksam).
Name (Kontakt)Nur bei Modultyp „Kontakt" sichtbar. Freier Anzeigename (max. 20 Zeichen), z. B. „Haustür".
Alarm beiNur bei Modultyp „Kontakt" sichtbar. „Offen" / „Geschlossen" / „Zustandswechsel" (Default „Offen"). „Zustandswechsel" ist kantengetriggert.

Modultyp-Auswahl rein manuell — ein offener Kontakt ist elektrisch nicht von „kein Modul gesteckt" unterscheidbar. Jeder Zustandswechsel wird ins lokale Ereignisprotokoll geschrieben. Der Kontakt ist rein lokal — keine MQTT-/SNMP-Anbindung. Der Schreibpfad (/api/relay) für das Relais wird von Weboberfläche, REST-API und — falls MQTT aktiv ist — von Home Assistant genutzt (Abschnitt 6.3), auch bei aktiver Automatik.

Relais, Kontakt und Sensor 2 noch nicht auf echter Hardware verifiziert
Das erste Testboard hatte weder ein Relais-, Kontakt- noch ein Sensor-2-RJ45-Modul gesteckt. Verkabelung/Pin-Zuordnung sind gegen das Herstellerdatenblatt geprüft (docs/verdrahtungsplan.html), das tatsächliche Schaltverhalten und die I2C-Erkennung realer Module stehen noch aus.

Zwei Wege, eine neue Firmware-Version einzuspielen:

5.1 Lokales OTA-Update über das Webinterface

  1. Neue .bin-Datei besorgen (z. B. von den GitHub-Releases, verlinkt unten auf der Einstellungsseite)
  2. Im Bereich „Firmware" die Datei auswählen und „.bin hochladen" klicken
  3. Nach erfolgreichem Upload startet das Gerät automatisch neu
Herkunfts- und Versionsprüfung
Die Firmware sucht im hochgeladenen Byte-Stream nach einem eingebetteten Marker (Projekt-ID SENSORMETER-POE + Version) und lehnt Uploads ab, die von einem Schwesterprojekt stammen oder eine ältere Version als die aktuell laufende sind. Ein Kontrollkästchen „Downgrade erzwingen" erlaubt bei Bedarf einen bewussten Rücksprung auf eine ältere Version (z. B. nach einer fehlerhaften Vorabversion).

Alternativ das Skript aus Abschnitt 1.3 im vorhandenen Checkout erneut ausführen — es aktualisiert den Quellcode (git pull, sofern keine lokalen Änderungen vorliegen) und flasht per natives USB neu (kein manueller Handgriff nötig, Abschnitt 1.2).

6.2 Syslog (UDP 514) & persistentes Log

Nur per UDP aktiv, wenn unter „Syslog" (Abschnitt 4.2) eine Server-IP ungleich 0.0.0.0 eingetragen ist. Drei Severity-Stufen (RFC5424-Konvention):

  • Statusreport — bei jedem Sensorzyklus (alle 60s), Severity „Informational" (6)
  • Fehler-Events — sofort bei Sensor-/Netzwerk-/NTP-Fehlern und echten Werksreset-Aktionen, Severity „Error" (3)
  • Warnungen — für transiente, selbstheilende Ereignisse (z. B. ein kurzer LAN-/WLAN-Aussetzer, der sich von selbst erholt), Severity „Warning" (4)

Unabhängig vom UDP-Versand schreibt das Gerät dieselben Ereignisse zusätzlich dauerhaft nach /log.txt auf der LittleFS-Datenpartition (32 KB je Datei, bei Überschreiten Rotation nach /log.old.txt, max. 64 KB gesamt) — abrufbar über den „Log"-Button auf der Hauptseite (Abschnitt 4.3), auch ohne konfigurierten Syslog-Empfänger. Praktisch, um die Vorgeschichte eines Geräts nachzuvollziehen, ohne dauerhaft einen Syslog-Server mitlaufen lassen zu müssen.

6.3 MQTT & Home Assistant (Discovery)

Nur aktiv, wenn unter „MQTT (Home Assistant)" (Abschnitt 4.2) sowohl „Aktiv" angehakt als auch eine Broker-Adresse eingetragen ist. Nutzt das etablierte Home-Assistant-MQTT-Discovery-Format.

TopicInhalt

Am ersten Testboard war kein MQTT-Broker konfiguriert. Discovery-Payload und Zustandssynchronisation mit Home Assistant sind daher noch nicht gegen einen echten Broker bestätigt.

6.4 Anbieter-Branding (Weisslabel)

Optionale Zusatzkennzeichnung, unabhängig vom Systemnamen: freier Anbietername und/oder ein Logo (Abschnitt 4.2). Beides einzeln optional — ohne beides bleibt das Gerät unverändert.

  • OLED (intern und optional extern): eigene Seite in der Rotation, nur wenn Name oder Logo gesetzt sind (siehe Abschnitt 3). Zeigt bevorzugt das Logo vollflächig, ohne Logo den Anbietername als Textzeile.
  • Weboberfläche: Logo (falls vorhanden) und Anbietername erscheinen im Kopfbereich jeder Seite.
  • Logo-Format: 128×64 Pixel, 1 Bit pro Pixel, MSB-zuerst je Zeile, exakt 1024 Byte (kein PNG/JPEG) — erzeugbar mit scripts/convert-logo.ps1.
Noch nicht auf echter Hardware verifiziert
Logo-Upload und -Anzeige (weder internes noch externes Display, weder Weboberfläche) sind am ersten Testboard noch nicht geprüft worden.

8Serial-Kommandozeile (USB)

Zusätzlich zur Weboberfläche lässt sich das Gerät direkt über die native USB-Verbindung steuern — ohne Netzwerkzugriff, ohne Passwort. Praktisch, wenn das Gerät nur per USB, aber nicht per Netzwerk erreichbar ist (z. Gleiches Vertrauensmodell wie beim BOOT-Taster
Wer das Gerät per USB-Kabel anschließen kann, gilt als vertrauenswürdig — kein Passwort nötig. Alle Kommandos außer reset/reset all sind nicht destruktiv.

8.2 Nutzung mit Windows-Boardmitteln (ohne Zusatzsoftware)

Für einen seriellen Terminal wird üblicherweise ein Zusatzprogramm wie PuTTY oder Tera Term verwendet — beides funktioniert, ist aber nicht vorinstalliert. Windows bringt mit der .NET-Klasse System.IO.Ports.SerialPort bereits alles Nötige mit; PowerShell (ab Windows 7 vorinstalliert) reicht für eine vollständige interaktive Sitzung, ganz ohne Download.

COM-Port ermitteln

Geräte-Manager öffnen (Win+X → Geräte-Manager) → „Anschlüsse (COM & LPT)" — das native USB-CDC-Gerät erscheint dort z. B. als „USB Serial Device (COM<n>)". Alternativ per PowerShell auflisten:

[System.IO.Ports.SerialPort]::GetPortNames()

Interaktive Sitzung (empfohlen)

Folgendes Skript als .ps1-Datei speichern (COM8 durch den tatsächlichen Port ersetzen) und mit powershell -ExecutionPolicy Bypass -File .\seriell.ps1 ausführen, oder direkt zeilenweise in ein PowerShell-Fenster einfügen:

$port = New-Object System.IO.Ports.SerialPort "COM8", 115200, "None", 8, "One"
$port.NewLine = "`n"
$port.Open()
Write-Host "Verbunden mit $($port.PortName). Kommando eingeben und Enter druecken."
Write-Host "Zum Beenden 'exit' eingeben."
while ($true) {
    Start-Sleep -Milliseconds 200
    while ($port.BytesToRead -gt 0) {
        try { Write-Host $port.ReadLine() } catch {}
    }
    $cmd = Read-Host
    if ($cmd -eq "exit") { break }
    $port.WriteLine($cmd)
}
$port.Close()

Das Skript öffnet den Port, gibt eingehende Zeilen laufend aus und sendet jede Eingabe als eigenes Kommando — genau wie ein grafisches Terminalprogramm, nur ganz ohne Installation. Für upload einfach die per dump angezeigten Zeilen (inkl. Marker) einzeln einfügen, jede mit Enter abschließen.

Einzelnes Kommando (Kurzform)

Für einen schnellen einmaligen Aufruf, z. B. nur den Status abfragen, genügt auch ein Einzeiler ohne Schleife:

$port = New-Object System.IO.Ports.SerialPort "COM8", 115200
$port.Open(); Start-Sleep -Seconds 3   # Boot-Log abwarten
$port.DiscardInBuffer()
$port.WriteLine("status")
Start-Sleep -Milliseconds 500
$port.ReadExisting()
$port.Close()
Natives USB-CDC: kurze Log-Lücke nach einem Reset
Auf dem ersten Testboard beobachtet: nach einem RTS-ausgelösten Reset (z. B. beim Öffnen eines Terminals) gehen die ersten Boot-Log-Zeilen gelegentlich verloren, bis der Host die USB-Neuanmeldung des Geräts abgeschlossen hat — eine Eigenschaft des nativen USB-CDC, kein Firmware-Fehler. Für zuverlässige Statusabfragen kurz nach einem Reset ggf. 2-3 Sekunden Wartezeit einplanen, wie im Beispiel oben.
